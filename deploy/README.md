# Свой сервер: бэкенд в Docker Compose

Бэкенд приложения — API routes (`/api/v1/*`): код из `src/app/api` и `src/server`, собранный `expo export --platform web --api-only` и запущенный на Node. Долгоживущий процесс держит в памяти очередь и результаты задач анализа (SPEC §7.1). Подходит для домашнего сервера (HP MicroServer и подобные, amd64 или arm64). До публичного релиза в том же compose работает и модель — на CPU, без GPU (SPEC D-6, промежуточное решение).

| Сервис       | Образ                                | Что делает                                                                                                                           |
| ------------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `api`        | собирается из `deploy/Dockerfile`    | API routes на Node (`server.js` + адаптер `expo-server`). Наружу не открыт.                                                          |
| `llm`        | `ollama/ollama:0.32.5`               | Модель (`LLM_MODEL`, по умолчанию `qwen3.6:35b-native`) на CPU: всегда в памяти, один анализ за раз, контекст 32K. Наружу не открыт. |
| `llm-pull`   | `ollama/ollama:0.32.5`               | При первом запуске скачивает модель в том `ollama-models`, создаёт из неё `-native` (см. «Модель») и завершается; `api` ждёт его.    |
| `pdf-render` | собирается из `deploy/pdf-render`    | Страницы PDF в JPEG для модели, которая читает только картинки (`pypdfium2`). Ничего не хранит, наружу не открыт.                    |
| `redis`      | `redis:8.10-alpine`                  | Счётчики лимитов и метрик беты (SPEC §8.3, §8.7), том `redis-data`. Документов и результатов анализа в нём нет.                      |
| `redis-http` | `hiett/serverless-redis-http:0.0.10` | REST API в формате Upstash поверх этого Redis: сервер работает с ним через `UpstashCounterStore`, обычным `fetch` без клиента Redis. |
| `caddy`      | `caddy:2.11-alpine`                  | HTTPS с сертификатом Let's Encrypt, `X-Real-IP` из адреса соединения (на нём держится лимит по IP). Журнала доступа нет.             |
| `tailscale`  | `tailscale/tailscale:v1.104.1`       | Только с `COMPOSE_PROFILES=funnel`: API из интернета через Tailscale Funnel, без домена и проброса портов (см. «Tailscale Funnel»).  |

## Что нужно

- Docker Engine с Compose v2 (`docker compose version`).
- Память: загруженная модель `qwen3.6:35b` с контекстом 128K занимает 27,7 ГиБ (`ollama ps` показывает 23 ГБ), PDF на 50 страниц — ещё до 3 ГиБ; всё остальное — меньше 1 ГБ. Нужно 32 ГБ и swap 4 ГБ (см. «Память» в разделе «Модель»). Диск: около 35 ГБ (модель, образ Ollama и сборка).
- Доменное имя, A/AAAA-запись которого указывает на внешний адрес сервера, и порты 80 и 443 с роутера на сервер. Без домена или без проброса портов (например, провайдер делит внешний IPv4 между абонентами, CGNAT) — аккаунт Tailscale для Funnel (см. «Tailscale Funnel»). Без того и другого сервер доступен только в локальной сети по HTTP (`API_DOMAIN=:80`): Android-сборка для такого адреса разрешает открытый HTTP сама (`app.config.js`, «Сборка приложения для этого сервера»), а iOS-сборкам нужен HTTPS.

## Первый запуск

```bash
git clone <репозиторий> docnavigator && cd docnavigator/deploy
cp .env.example .env
```

Заполните в `deploy/.env` три обязательные переменные: `API_DOMAIN`, `DEVICE_ID_HASH_KEY`, `COUNTER_STORE_TOKEN` (секреты — `openssl rand -hex 32`). `DEVICE_ID_HASH_KEY` после запуска не меняйте: новый ключ обнуляет дневные лимиты и разрывает метрики беты. Для push о готовности анализа (ANL-12) нужен ещё `EXPO_ACCESS_TOKEN` — токен доступа аккаунта Expo при включённой защите push в проекте EAS; без него push не отправляется, и приложение получает результат, когда его откроют.

```bash
docker compose up -d --build
docker compose ps
```

Первый запуск скачивает модель (24 ГБ): `up` ждёт, пока `llm-pull` закончит, прогресс — `docker compose logs -f llm-pull`. Последующие запуски находят модель в томе и не качают её снова.

Проверка снаружи (сертификат Caddy получает за несколько секунд после первого запроса):

```bash
curl https://api.example.com/healthz
curl https://api.example.com/api/v1/limits -H 'X-App-Version: 1.0.0' -H 'X-Platform: android' -H 'X-Device-Id: 6f1c2a9e-3b7d-4c8e-9f0a-1b2c3d4e5f60'
```

Приложение направляется на сервер переменной `EXPO_PUBLIC_API_URL=https://api.example.com` (в `.env.local` для dev-сервера, при сборке — см. ниже). Анализ асинхронный: приложение загружает документ, а результат забирает, когда модель закончит, поэтому минуты на CPU ему не мешают (SPEC D-1).

## Tailscale Funnel

Без домена или проброса портов API публикует сервис `tailscale` через [Tailscale Funnel](https://tailscale.com/kb/1223/funnel): адрес `https://<TS_HOSTNAME>.<tailnet>.ts.net` с настоящим сертификатом, роутер ничего не пробрасывает. Контейнер сам соединяется с Tailscale и заканчивает TLS, поэтому ретрансляторы Tailscale передают только зашифрованный трафик и видят лишь адрес клиента. Этот адрес `tailscaled` кладёт в `X-Forwarded-For` вместо присланного клиентом, а Caddy верит заголовку только на входе Funnel (`127.0.0.1:8081` в своей сети, снаружи и из других контейнеров недоступен), поэтому лимит по IP считает адрес клиента.

1. Аккаунт Tailscale ([login.tailscale.com](https://login.tailscale.com)). В консоли: **DNS** — включены MagicDNS и HTTPS Certificates; **Access controls** — Funnel в политике (кнопка «Add Funnel to policy» или вручную `"nodeAttrs": [{ "target": ["autogroup:member"], "attr": ["funnel"] }]`).
2. В `deploy/.env`: `COMPOSE_PROFILES=funnel`, при желании `TS_HOSTNAME` (по умолчанию `docnavigator`). `API_DOMAIN=:80` оставьте: в локальной сети API по-прежнему отвечает по HTTP. `.env` — ещё и `env_file` сервиса `api`, поэтому после правки он пересоздаётся и теряет очередь; если это некстати, поднимайте только нужный сервис: `docker compose up -d --no-recreate tailscale`.
3. Вход — один раз, ключом: в консоли **Settings → Keys → Generate auth key** (не Reusable, не Ephemeral). Ссылка для входа из `docker compose logs tailscale` не годится: контейнер ждёт подтверждения 60 секунд, потом перезапускается с новой ссылкой. Поэтому вход — отдельным контейнером на том же томе (`docnavigator_` — имя проекта compose); ключ вводится без эха и в командную строку не попадает:

   ```bash
   docker compose stop tailscale
   docker run -d --name tailscale-login -v docnavigator_tailscale-state:/var/lib/tailscale tailscale/tailscale:v1.104.1 tailscaled --statedir=/var/lib/tailscale --tun=userspace-networking --socket=/tmp/tailscaled.sock
   read -rs key; printf '%s' "$key" | tr -d '[:space:]' | docker exec -i tailscale-login sh -c 'umask 077; cat > /tmp/authkey'; unset key
   docker exec tailscale-login tailscale --socket=/tmp/tailscaled.sock login --hostname=docnavigator --accept-dns=false --auth-key=file:/tmp/authkey
   docker rm -f tailscale-login && docker compose up -d --no-deps tailscale
   ```

   `invalid key` чаще всего значит, что вместе с ключом вставилось лишнее (например, `--auth-key=`). Вход хранится в томе `tailscale-state`, ключ после него недействителен.

4. В консоли, **Machines** → эта машина → **Disable key expiry**: иначе через 180 дней вход истекает, и Funnel перестаёт отвечать.
5. Адрес — `docker compose exec tailscale tailscale funnel status`. DNS-запись появляется до 10 минут, сертификат выдаётся при первом запросе.

```bash
curl https://docnavigator.<tailnet>.ts.net/healthz
```

Приложение собирается с `EXPO_PUBLIC_API_URL=https://docnavigator.<tailnet>.ts.net` (ниже). Funnel — бета Tailscale: скорость трафика ограничена, лимиты не настраиваются и не опубликованы; слушать можно только порты 443, 8443 и 10000.

## Сборка приложения для этого сервера

`EXPO_PUBLIC_API_URL` попадает в бандл при сборке. Release APK для Android на своей машине (бесплатно, без EAS), для сервера в локальной сети:

```bash
export EXPO_PUBLIC_API_URL=http://192.168.1.101   # адрес сервера; с доменом — https://api.example.com
npx expo prebuild --platform android --clean       # app.config.js разрешает HTTP только для http://-адреса
cd android && ./gradlew --no-daemon assembleRelease
adb install -r app/build/outputs/apk/release/app-release.apk
```

Переменная из окружения сильнее `.env.local`, а `--no-daemon` не даёт Gradle взять окружение старого демона. Такая сборка подписана отладочным ключом: её можно поставить через `adb`, но не опубликовать. Адрес в локальной сети работает, только пока телефон в той же сети.

## Обновление и обслуживание

```bash
git pull && docker compose up -d --build   # пересобрать и заменить api; анализу в работе даётся 95 с, более долгий обрывается
docker compose logs -f api                 # события upload.*, analysis.*, push.sent, одна строка JSON (modelMs — сколько думала модель)
curl -H "Authorization: Bearer $METRICS_TOKEN" https://api.example.com/api/v1/metrics   # отчёт беты, если задан METRICS_TOKEN
```

Логи каждого контейнера ротируются: 5 файлов по 10 МБ. В них только метаданные (SPEC §7.1).

## Что важно знать

- Память ограничивает очередь (`ANALYSIS_QUEUE_MAX`, до 20 документов по 20 МБ) и модель. Перезапуск `api` теряет очередь и незабранные результаты: приложение получает `404` и предлагает повторить (SPEC §7.1).
- `requestId` в логах — UUID, который сервер создаёт сам. Логи — в `docker compose logs`.
- Счётчики — в локальном Redis. Резервная копия нужна только если важны метрики беты: том `docnavigator_redis-data`.
- Модель своя (`OpenAiCompatibleProvider` → Ollama): документы не уходят AI-провайдеру, анализ бесплатный (`costUsd: 0`), но медленный.

## Модель

- **Скорость.** На CPU документ из нескольких страниц разбирается за минуты, длинный PDF — дольше. Запросы идут по одному: следующий ждёт, пока модель закончит предыдущий. Рассуждения выключены (`LLM_REASONING_EFFORT=none`), с ними было бы в разы дольше. Замер на HPE MicroServer (Xeon E-2414, 4 ядра, 2026-10-20, `qwen3.6:35b`, с памяткой): фото из 1 страницы — 4,8 мин, PDF из 2 страниц — 7,2 мин; модель читает текст промпта со скоростью около 50 токенов/с, страницу (около 1,5–2 тыс. токенов) — около 2 мин, и пишет ответ около 9 токенов/с (ответ — 1–2 тыс. токенов). Первый анализ после запуска ещё 1–2 мин грузит модель в память. Следующие анализы на 1,7 мин быстрее: системное сообщение уже прочитано (ниже). PDF из 50 страниц (2026-11-03, 92,7 тыс. токенов): промпт читается 2,4 ч (около 11 токенов/с), ответ пишется 1,6 токена/с; оба синтетических PDF из 50 страниц дописали ответ до предела в 8192 токена за 3,8 ч и закончились `analysis_failed`.
- **Системное сообщение читается один раз.** Правила и правовая памятка (около 4,8 тыс. токенов, 1,7 мин) одинаковы для всех документов, и модель читает их только в первом анализе после запуска. `qwen3.6` — гибридная модель: llama.cpp внутри Ollama умеет вернуть её состояние только к сохранённой контрольной точке, а точку на границе сообщений ставит, только когда сам применяет шаблон чата модели. Собственный шаблон Ollama (у `qwen3.6:35b`) этого не делает, и каждый анализ читал промпт с начала. Поэтому по умолчанию `LLM_MODEL=qwen3.6:35b-native`: `llm-pull` создаёт его из `qwen3.6:35b` без шаблона Ollama — те же файлы, места на диске не занимает, но при создании около 7 мин читает 22 ГБ. Суффикс `-native` работает и с другой моделью. Замер 2026-10-20, два разных фото страницы подряд: второе — 232 с вместо 387 с, чтение промпта — 126 с вместо 231 с. Ответы модели от запуска к запуску немного различаются и без этого, формат тот же. Ollama считает `qwen3.6:35b` и `qwen3.6:35b-native` одной моделью и не перезапускает её с другим шаблоном: после ручных запросов к `qwen3.6:35b` выполните `docker compose exec llm ollama stop qwen3.6:35b`. Модель помнит только последний промпт (кэш промптов в памяти выключен, «Память» ниже), поэтому памятку она читает заново и после запроса с другим началом: прогона оценки со своим промптом или ручного запроса через туннель.
- **Контекст.** 32K токенов хватает на промпт и около 15 страниц: страница — около 1,5–2 тыс. токенов картинки, длинная сторона до 1600 px, а системное сообщение с правовой памяткой (SPEC §7.4, правило 11) — около 5 тысяч. Больше страниц — поднимите `LLM_CONTEXT_LENGTH`, это стоит памяти: PDF на 50 страниц (предел SPEC CAP-7) — до 105 тысяч токенов, ему нужен `LLM_CONTEXT_LENGTH=131072`. С 32K такой PDF в контекст не помещается.
- **Память.** Замер 2026-11-03 на HPE MicroServer (31,25 ГиБ памяти, swap 4 ГиБ, `LLM_CONTEXT_LENGTH=131072`): два PDF по 50 страниц и за ними PDF из 1 страницы, каждый начинался сразу после предыдущего. Загруженная модель без запросов — 27,7 ГиБ (RSS `llama-server`; из них веса — 20,2 ГиБ, KV-кэш — 2,9 ГиБ, буферы вычислений — 2,3 ГиБ, энкодер картинок — 0,8 ГиБ), свободно 2,25 ГиБ. К концу чтения PDF на 50 страниц — 28,9 ГиБ (12 контрольных точек по 72 МБ и картинки страниц), свободно 1 ГиБ. Больше всего — в начале следующего анализа, когда в памяти картинки и старого, и нового промпта: 29,7 ГиБ в памяти и 1,3 ГиБ в swap, свободно 0,26 ГиБ, swap занят на 2,2 из 4 ГиБ. После трёх анализов — 28,8 ГиБ и 1,4 ГиБ в swap, свободно 1,2 ГиБ памяти и 1,6 ГиБ swap. Без swap процесс в этот момент не поместился бы: не отключайте его. С контекстом 32K KV-кэш меньше на 2 ГиБ (расчёт по логу `llama-server`, не замер). Если памяти не хватает — меньше `LLM_CONTEXT_LENGTH` или модель поменьше (ниже).
  `LLAMA_ARG_CACHE_RAM=0` в `compose.yaml` выключает кэш промптов `llama-server` в памяти (по умолчанию до 8 ГБ): в начале следующего запроса он копировал туда предыдущий промпт целиком. 2026-11-02 после PDF на 46 страниц (88 тыс. токенов) копия заняла 1,8 ГБ и ещё контрольные точки, ядро убило `llama-server` (30,2 ГиБ в памяти и 3,7 ГиБ в swap), и оба ждавших запроса получили `500`.
- **Другая модель:** `LLM_MODEL` в `.env`, например `gemma4:12b` (8 ГБ) при нехватке памяти; `llm-pull` скачает её при следующем `up`. Модель снаружи (SPEC D-6, варианты B и C): `LLM_BASE_URL` и `LLM_API_KEY`; сервисы `llm` и `llm-pull` тогда можно убрать.
- **Без модели:** `LLM_PROVIDER=mock` отвечает синтетическими фикстурами.
- **Модель не скачивается.** `llm-pull` не завершается, а в `docker compose logs llm` — `dial tcp …:443: i/o timeout` к `r2.cloudflarestorage.com`. Так бывает, когда хранилище Cloudflare R2 из вашей сети недоступно по IPv4, а у сети Docker нет IPv6. Скачайте модель контейнером с сетью хоста в тот же том, он слушает только `127.0.0.1`:

  ```bash
  docker compose stop llm-pull llm
  docker run -d --name model-download --network host -e OLLAMA_HOST=127.0.0.1:11435 -v docnavigator_ollama-models:/root/.ollama ollama/ollama:0.32.5
  docker exec -e OLLAMA_HOST=127.0.0.1:11435 model-download ollama pull qwen3.6:35b
  docker rm -f model-download && docker compose up -d
  ```

## Если на сервере уже есть обратный прокси

Уберите сервис `caddy` и откройте порт `api` (`ports: ['127.0.0.1:3000:3000']`). `TRUST_PROXY: 'true'` оставляйте только если прокси перезаписывает `X-Real-IP` адресом клиента, иначе клиент сам выбирает свой адрес и обходит лимит по IP. Без `TRUST_PROXY` сервер берёт адрес из TCP-соединения.

## Проверка на своей машине

`API_DOMAIN=:80`, `HTTP_PORT=8088`: Caddy отдаёт API по HTTP на `http://localhost:8088`. Если памяти меньше 32 ГБ, `LLM_MODEL=gemma4:e2b` (около 5 ГБ) проверит связку, но не качество.
