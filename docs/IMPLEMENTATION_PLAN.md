# Навигатор по документам: план имплементации MVP

Основан на [SPEC.md](./SPEC.md). Ссылки вида CAP-2 и §7.3 ведут к требованиям и разделам спецификации.

## Принципы

- **Сначала сквозной сценарий на заглушке.** `MockLlmProvider` позволяет собрать путь «скан → анализ → экран документа → напоминание» до выбора реального LLM-провайдера.
- **Одна задача — один PR.** Каждая задача заканчивается зелёным `npm run verify` и тестами рядом с кодом.
- **Проектные скиллы.** `new-feature`, `new-screen`, `new-component`, `api-integration`, `add-dependency`, `write-tests` описывают соглашения репозитория. Колонка «Скилл» в таблицах указывает, какой из них использовать.
- **Чистая логика отдельно от платформы.** Расчёт напоминаний, обработку дат и валидацию ответа пишем как чистые функции с unit-тестами. Нативные модули (сканер, уведомления, календарь) прячем за тонкими адаптерами с `.web.ts`-заглушками.
- **Платные и публичные действия только с подтверждения:** `eas build`, `eas deploy`, `eas submit`, `eas update`, установка зависимостей.

## Целевая структура кода

```
src/
  app/                          маршруты (тонкие) + API routes
    (tabs)/index.tsx, deadlines.tsx, settings.tsx
    capture/index.tsx, review.tsx
    documents/[id].tsx, documents/[id]/pages.tsx
    onboarding.tsx
    api/v1/analyze+api.ts, limits+api.ts
  features/
    capture/                    сканер, выбор файла, нормализация, экран проверки
    documents/                  репозиторий документов, список, экран документа
    analysis/                   запрос анализа, мутация, сохранение результата, блоки результата
    deadlines/                  вкладка «Сроки», редактирование срока
    reminders/                  planReminders(), syncReminders(), адаптер уведомлений
    onboarding/                 онбординг и согласие
    settings/                   настройки
  lib/
    db/                         открытие SQLite, миграции
    files/                      хранение файлов документа
    i18n/                       настройка локализации, словари ru/en
    device-id.ts
    api/client.ts               + поддержка FormData и таймаута
  shared/
    analysis/                   zod-схема AnalysisResult, типы, лимиты (клиент + сервер)
  server/                       ТОЛЬКО для src/app/api/**/*+api.ts
    analysis/                   обработчик, промпт, провайдеры (mock, <provider>), пост-обработка
    limits/                     лимиты и бюджет
scripts/eval/                   оценка качества анализа на тестовом наборе
```

## Этапы

```mermaid
flowchart LR
  E0[0. Подготовка и спайки] --> E1[1. Фундамент]
  E1 --> E2[2. Захват документа]
  E1 --> E3[3. Бэкенд анализа]
  E2 --> E4[4. Анализ в приложении]
  E3 --> E4
  E4 --> E5[5. Сроки и напоминания]
  E5 --> E6[6. Качество и бета]
```

Этапы 2 и 3 можно вести параллельно: их связывает только общая схема из задачи 1.2. Чистую логику напоминаний (задача 5.2) можно начать сразу после этапа 1.

Размеры задач: **S** — до 1 дня, **M** — 1–3 дня, **L** — 3–5 дней.

## Оценка

Грубая оценка для одного разработчика, без учёта ожидания ответов и ревью сторов:

| Этап                   | Дней                      |
| ---------------------- | ------------------------- |
| 0. Подготовка и спайки | 4–6                       |
| 1. Фундамент           | 5–7                       |
| 2. Захват документа    | 4–5                       |
| 3. Бэкенд анализа      | 6–8                       |
| 4. Анализ в приложении | 8–10                      |
| 5. Сроки и напоминания | 5–7                       |
| 6. Качество и бета     | 6–8                       |
| **Итого**              | **38–51 (≈ 8–10 недель)** |

С двумя разработчиками (клиент и бэкенд параллельно на этапах 2–3) получится примерно 6–7 недель.

## Риски

| Риск                                                              | Вероятность | Влияние | Что делаем                                                                                                                                |
| ----------------------------------------------------------------- | ----------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| EAS Hosting не держит большие тела запросов или долгие ответы LLM | средняя     | высокое | Спайк 0.2. Запасные варианты: потоковый ответ, асинхронная задача с временным хранилищем и TTL, отдельный сервис с тем же контрактом API. |
| Плагин сканера несовместим с RN 0.88 или New Architecture         | средняя     | высокое | Спайк 0.4. Запасные варианты: другая обёртка VisionKit и ML Kit, свой Expo-модуль, временно камера без поиска краёв.                      |
| LLM ошибается в датах или выдумывает сроки                        | высокая     | высокое | Цитаты из оригинала, пометка «рассчитано», ручное редактирование, пост-валидация, eval-набор, дисклеймер                                  |
| Затраты на LLM растут быстрее аудитории                           | средняя     | среднее | Дневные лимиты, общий бюджет, сжатие изображений, выбор модели по соотношению цена/качество                                               |

## Что нужно от вас, чтобы начать

1. **Подтвердить зависимости** из SPEC §10. Ничего не устанавливается без вашего согласия.
2. **Ответить на открытые вопросы 1–4** из SPEC §11: название и идентификаторы приложения, страны запуска, размер лимита, минимальные версии ОС.
3. **API-ключи 2–3 LLM-провайдеров** для сравнения в задаче 0.3. Они хранятся в `.env.local` и в git не попадают.
4. **Разрешить `eas deploy` и `eas build`** для спайков и сборок (бесплатные квоты EAS или платный план).
5. **Тестовые документы:** дать обезличенные примеры или согласовать синтетический набор.
