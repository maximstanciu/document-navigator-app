# Спайк 0.2: EAS Hosting

Задача 0.2 из [плана](../IMPLEMENTATION_PLAN.md). Проверяли, выдержит ли EAS Hosting синхронный запрос анализа из SPEC §7.2: тело `multipart/form-data` до 20 МБ, ожидание ответа модели до 60 с, память изолята, обрыв соединения клиентом.

## Как мерили

Временный маршрут `POST /api/spike/upload` повторял путь будущего `/api/v1/analyze` до вызова модели: `request.formData()` → байты файла → base64 через `Buffer` → JSON-тело в формате запроса к LLM → исходящий `fetch`. Параметры запроса включали этапы по отдельности (только разбор, разбор и кодирование, полный путь), добавляли лишние выделения памяти и задавали задержку ответа.

Публичные сервисы с задержкой (httpbin, postman-echo) отвечают не позже чем через 10 с. Поэтому медленную модель изображал второй маршрут того же деплоя `/api/spike/slow`: он принимает тело и отвечает через заданное время. Выяснилось, что Worker может обращаться к собственному деплою.

Внутри Workers `Date.now()` не идёт во время вычислений, поэтому процессорное время изнутри не измерить. Время ниже — полное время запроса со стороны клиента, включая загрузку по сети.

## Выводы

1. **Синхронный запрос на 60–90 с работает.** Для варианта A решения D-1 запасные схемы (потоковый ответ, асинхронная задача, отдельный сервис) из-за длительности не нужны.
2. **Довести вызов модели после обрыва нельзя.** Обработчик отменяется вместе с исходящим запросом. Вариантам B и C решения D-1 понадобится очередь или отдельный сервис: `waitUntil` по документации Cloudflare даёт только 30 с после ответа (в спайке не проверяли).
3. **Обрыв на сервере не увидеть, но и лимит списывать не придётся.** Если засчитывать анализ в дневной лимит только после ответа модели, код списания после обрыва просто не выполнится. Вызов провайдера при этом уже начат и может быть оплачен частично. От злоупотреблений «начать и оборвать» защищают лимит по IP и общий бюджет.
4. **Главный риск — память при нескольких больших документах одновременно.** Один упавший изолят роняет все запросы в нём, включая уже оплаченные вызовы модели. Что делать:
   - в обработчике 3.1 держать как можно меньше копий: не хранить `File` и `ArrayBuffer` после кодирования, отпускать ссылки до `await fetch`. Цель — не больше трёх размеров файла, проверить тем же замером (4 одновременных запроса по 20 МБ проходят);
   - если цель не достигается, снизить лимит размера с 20 до 10 МБ (CAP-7). 30 нормализованных страниц весят 9–18 МБ, обычный документ из 1–3 страниц — до 2 МБ, так что крупными бывают в основном PDF.
5. **Ответ при падении изолята — не JSON.** Клиент (4.1) должен считать любой `5xx` без JSON-тела ошибкой `unavailable` и предлагать повтор.
6. **Тариф.** Для разработки и закрытой беты хватает Free. До публичного релиза перейти на Starter: лимит 10 мс CPU на Free задокументирован и может начать действовать.
7. **Типы.** Глобальный `FormData` в проекте описан типами React Native, а не Workers. Серверному коду в 3.1 нужны свои типы для файлов из `formData()`.

## Что не проверено

- Логи и метрики в дашборде EAS: видно ли `console.log`, есть ли в списке запросов оборванные. Для этого нужен вход на expo.dev в браузере.
- `waitUntil` и как он доступен из Expo API routes.
- Загрузка с телефона по мобильной сети. При 1 МБ/с 20 МБ добавят к анализу около 20 с.
- Ограничения на размер запроса у настоящего LLM-провайдера (§7.5). Это задача 0.3.
- Поведение на платных планах.
